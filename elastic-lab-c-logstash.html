Logstash structures a log with grok

Filebeat's modules know how to read logs that thousands of people share, like syslog and Zeek. Your own applications write logs nobody has a module for. Logstash is where you teach the stack to read them: a pipeline receives raw lines, a grok filter cuts each line into named fields, and the result goes to Elasticsearch with the right types. In this lab you build the pattern in Kibana's Grok Debugger, let Logstash take its pipelines from Kibana instead of from files, create the pipeline in Stack Management → Logstash Pipelines, and watch a mapping mistake happen and get fixed. Every number and screenshot here comes from running these steps on the class stack.

1A log nobody has a module for

client-01 Write thirty login records the way a small web application might. Each line is a time, a level, a user, an address, an action, a result and a duration. Every fourth one is admin failing.

cd /home/ubuntu/data/lab
users=(alice bob carol admin)
for i in $(seq 1 30); do
  u=${users[$((i % 4))]}
  lvl=INFO; res=success
  if [ "$u" = admin ]; then lvl=WARN; res=failure; fi
  ts=$(date -u +%Y-%m-%dT%H:%M:%SZ)
  echo "$ts $lvl $u 172.21.0.5 login $res $((20 + i))ms" >> app.log
done

Thirty lines, seven failures. Those two numbers are what Elasticsearch must show at the end.

2Build the pattern in the Grok Debugger

A grok pattern is the line, rewritten as named pieces. %{IP:src_ip} means "here is something shaped like an IP address; call it src_ip". :int on the end makes the value a number instead of text. Logstash ships with hundreds of named shapes: TIMESTAMP_ISO8601, LOGLEVEL, USERNAME, WORD, NUMBER.

Kibana Menu → Management → Dev Tools → Grok Debugger. Paste one line from app.log into Sample Data, and this into Grok Pattern, all on one line:

%{TIMESTAMP_ISO8601:timestamp} %{LOGLEVEL:level} %{USERNAME:user} %{IP:src_ip} %{WORD:action} %{WORD:outcome} %{NUMBER:duration_ms:int}ms

Click Simulate. Every piece comes back named, and duration_ms is the number 23, not the text "23".

If a piece is wrong, the debugger returns nothing at all. Change one piece at a time until it matches; that is how every grok pattern is written.

Why not an API key, as in Lab A? It was the first thing tried on the class stack. The key was created in the Console with a role descriptor limiting it to those two privileges:

Logstash then refused to start:

Logstash will not send an API key over plain HTTP, and this stack has no TLS. A password from the Logstash keystore is the safe choice here. If you made such a key, revoke it as in Lab A.

4Create the pipeline

The pipeline has three parts. input: listen for Filebeat on port 5044. filter: grok cuts the line, date makes the line's own time the event's time, and mutate renames the pieces to the standard ECS names. The pattern is the one from the debugger, split into two named parts with pattern_definitions so each line stays short. output: send to Elasticsearch as docker-elk's logstash_internal user, whose password Logstash already reads from its environment.

input {
  beats {
    port => 5044
  }
}

filter {
  grok {
    pattern_definitions => {
      "WHO"  => "%{USERNAME:user} %{IP:src_ip}"
      "WHAT" => "%{WORD:action} %{WORD:outcome} %{NUMBER:duration_ms:int}ms"
    }
    match => {
      "message" => "%{TIMESTAMP_ISO8601:ts} %{LOGLEVEL:level} %{WHO} %{WHAT}"
    }
  }
  date {
    match => ["ts", "ISO8601"]
    remove_field => ["ts"]
  }
  mutate {
    rename => {
      "level"   => "[log][level]"
      "user"    => "[user][name]"
      "src_ip"  => "[source][ip]"
      "action"  => "[event][action]"
      "outcome" => "[event][outcome]"
    }
  }
}

output {
  elasticsearch {
    hosts    => "elasticsearch:9200"
    user     => "logstash_internal"
    password => "${LOGSTASH_INTERNAL_PASSWORD}"
    index    => "logstash-applog"
  }
}

5Ship app.log through Logstash

Filebeat may have only one output, and the Filebeat from Lab A already sends to Elasticsearch. So start a second Filebeat with its own small configuration and its own registry folder. Lab A's Filebeat keeps running untouched.

client-01

cat > /etc/filebeat/to-logstash.yml <<'EOF'
filebeat.inputs:
  - type: filestream
    id: applog
    paths:
      - /home/ubuntu/data/lab/app.log

output.logstash:
  hosts: ["logstash:5044"]
EOF
C="-c /etc/filebeat/to-logstash.yml --path.data /var/lib/filebeat-ls"
filebeat test config $C
filebeat test output $C
nohup filebeat -e $C > /var/log/filebeat-ls.log 2>&1 &
Config OK
logstash: logstash:5044...
  ...
  talk to server... OK

No password here: Logstash's beats input accepts any sender on the Docker network. That is fine inside this lab and is the next thing to fix anywhere real.

30 documents. Each one has user.name, source.ip, event.action, event.outcome, log.level and duration_ms, and its @timestamp is the time written in the line. But the mapping is wrong:

"source.ip" : { "mapping" : { "ip" : { "type" : "text", "fields" : { "keyword" : ...

source.ip was stored as text, not ip. Ask how many logins failed per user, and Elasticsearch refuses:

Fielddata is disabled on [event.outcome] in [logstash-applog]. Text fields are not optimised for
operations that require per-document field data like aggregations and sorting ...

Nobody told Elasticsearch what these fields are, so it guessed from the first document: every string became text. Grok gave the pieces names; only an index template gives them types.

6Fix the mapping

Logstash installs an index template called ecs-logstash for every index whose name starts with ecs-logstash-. It knows the ECS fields: source.ip is an address, user.name and event.outcome are keywords. So the fix is one word in the output: the index name.

Kibana UI

Logstash Pipelines, click cis3370-applog, change the last line of the output to index => "ecs-logstash-applog", and deploy again.
