Zeek, from a capture to Elasticsearch

Lab A shipped what a host writes about itself. This lab ships what the network says. Zeek reads packets and writes one record per connection, DNS query, web request and TLS handshake. You will run it on the Lecture 6 capture twice, once in its default text format and once in JSON, and measure the difference. Then you will ship the records to Elasticsearch as raw lines and through Filebeat's Zeek module, find the port scan hidden in the capture, and finally point Zeek at zeek-lab's own network card while you make traffic and client-01 scans it. Every number and screenshot here comes from running these steps on the class stack.

This is TSV, tab-separated values. Every record is one line of values, and the eight lines starting with # say what the columns are, what type each is, and how a missing value is written (-). JSON costs disk, and buys records that every tool can read without knowing Zeek's header conventions, one line at a time, with the full precision Zeek measured. For a log you ship somewhere else, that trade is almost always worth it.

Zeek invents a new uid each run, so yours differ. Every other value comes from the packets and matches.

Way one: conn.log as a raw stream

zeek-lab The same filestream input as Lab A, plus the ndjson parser, which turns each JSON line into fields. target keeps them under one name so they cannot collide with anything else.

cp /etc/filebeat/filebeat.yml /etc/filebeat/filebeat.yml.original
cat > /etc/filebeat/filebeat.yml <<'EOF'
filebeat.inputs:
  - type: filestream
    id: zeek-conn-raw
    paths:
      - /home/ubuntu/data/zeek-logs/conn.log
    parsers:
      - ndjson:
          target: "zeek_raw"
    fields:
      lab: zeek-stream

filebeat.config.modules:
  path: ${path.config}/modules.d/*.yml
  reload.enabled: false

output.elasticsearch:
  hosts: ["http://elasticsearch:9200"]
  username: "beats"
  password: "${ES_PWD}"
EOF

Way two: the zeek module

filebeat modules enable zeek
nano /etc/filebeat/modules.d/zeek.yml

5Zeek, live, on its own network card

So far Zeek read a recording. Now it watches zeek-lab's network card while you make traffic, and Filebeat ships each record as Zeek writes it. The module already lists the zeek-live folder, so Filebeat needs no change: when the files appear, it finds them within about 10 seconds.

zeek-lab

mkdir -p /home/ubuntu/data/zeek-live && cd /home/ubuntu/data/zeek-live
nohup /opt/zeek/bin/zeek -C -i eth0 LogAscii::use_json=T > zeek.out 2>&1 &
hostname -i

-i eth0 means listen on the network card. Note the address. Then restart Filebeat, so that its own connection to Elasticsearch begins while Zeek is watching. Zeek can only decode a conversation it saw start; a connection opened before Zeek started is just bytes to it.

pkill filebeat
nohup filebeat -e > /var/log/filebeat-run.log 2>&1 &

Now make traffic from zeek-lab itself:

curl -s -o /dev/null -w "%{http_code}\n" http://example.com/
curl -s -o /dev/null -w "%{http_code}\n" https://www.elastic.co/
apt-get update

host docker compose exec client-01 bash, then in client-01:

apt-get install -y nmap
nmap -sT -p 1-1000 zeek-lab
hostname -i

...

On the class stack, with zeek-lab at 172.21.0.5 and client-01 at 172.21.0.7: 1,044 documents, made of 1,018 zeek.connection, 25 zeek.http and 1 zeek.ssl. 1,000 connections came from client-01, all REJ: the scan, seen by its target a few seconds after it happened. The capture's bundle counts did not change; Filebeat's registry knows it already sent those files.

Three things the live capture teaches

  • No dns.log at all. Docker answers name lookups inside the container, at 127.0.0.11, over the loopback interface. The queries never cross eth0, so a sensor on eth0 cannot see them. Where you put a sensor decides what it can see.
  • https:// is one ssl record; http:// is a full http record. For the encrypted site Zeek knows the server name and certificate. For example.com it knows the method, the path, the status code and the user agent.
  • Zeek watched Filebeat ship the logs. On the class stack 19 of the 25 http records were Filebeat talking to elasticsearch:9200, and each one carried user.name: beats. Skip the Filebeat restart and they are missing, because Zeek never saw that connection begin. This stack speaks plain HTTP, so the account name, and the password with it, cross the network in the clear.

6Questions

Question 1

Give two reasons to ship Zeek in JSON and one reason not to, each with a number you measured.

Question 2

A detection rule counts refused connections per minute. What would it report on the raw stream, given where its @timestamp comes from? Why is that dangerous?

Question 3

The capture shows 2,000 refusals and the live scan 1,000, from the same kind of nmap command. Explain the difference.

Question 4

Choose a threshold: how many REJ from one source in 60 seconds should raise an alert? Justify it with the 24 ordinary connections in the capture, and name a scan your threshold would miss.

Question 5

Your sensor saw no DNS. Where would you put it to see every lookup the lab machines make, and what would it still miss?

Question 6

Zeek recorded user.name: beats in Filebeat's own traffic. What exactly would an attacker on this network learn, and what single change to the stack stops it?
