1The test set contains attacks the training set never shows

Analysis

Counted the distinct values of Class in each file and compared the two sets. Training has 22 attack types. Test has 37. 17 of them appear only in test, covering 3,750 test rows (16.6% of the test set).

Issue detected

A model can only learn patterns it has seen. One test row in six belongs to an attack type that was absent from training, so no amount of tuning will teach the model those rows. This is deliberate in NSL-KDD: it simulates tomorrow's attacks.

Tools available

Set comparison on the label column. A frequency table per file. No statistics needed yet, only careful counting.

Solution

Report two accuracies: one on the attacks the model was trained on, one on the unseen ones. Never quote a single overall number without saying which. If the goal is catching novel attacks, an anomaly detector trained only on normal traffic is the honest design, not a classifier.

2Train and test do not have the same shape

Analysis

Compared each family's share of its file. R2L is 0.8% of training but 12.8% of test, roughly a sixteenfold shift. U2R moves from 0.0% to 0.3%.

Issue detected

The test set is not a random sample of the training set. A model tuned to do well on the training mix is being graded on a different mix, so cross-validation scores on the training file will look far better than test performance. That gap is the dataset's design, not your mistake.

Tools available

Two-proportion comparison, or a chi-square goodness-of-fit test between the observed test counts and the proportions expected from training. The p-value answers one question: if the two files really came from the same population, how surprising is a difference this large? A very small p-value means "this gap is not luck."

Solution

Split a validation set from the training file for tuning, then treat KDDTest+ as a final exam you look at once. Expect the drop and explain it, rather than tuning until the test number improves, which is how people quietly overfit the test set.

3One class is almost absent

Analysis

U2R has 52 rows in 125,973 training rows, which is 0.0%. The largest class, normal, has 67,343.

Issue detected

Accuracy becomes meaningless. Predicting normal for every test row scores 43.1% without a model at all. A classifier can ignore U2R entirely and still look excellent.

Tools available

The majority-class baseline, which is the number every model must beat. A confusion matrix. Precision, recall and F1 per class. For imbalance, precision-recall curves are more honest than ROC.

Solution

Report per-class recall, not overall accuracy. Use stratified splits so rare classes appear in every fold, and class weights so errors on U2R cost more than errors on normal. Resampling such as SMOTE is an option, but on 52 real examples it invents most of what it trains on, so treat it with suspicion.

4A column that says nothing

Analysis

Checked every feature for how many distinct values it takes. Num_Outbound_Commands is 0 in all 125,973 training rows.

Issue detected

A column with no variation cannot separate anything. It costs memory, adds a term to every model, and breaks correlation calculations because dividing by a zero standard deviation is undefined.

Tools available

Variance of each column, or simply a count of distinct values. This is the cheapest check in the whole pipeline.

Solution

Drop zero-variance columns before anything else, and record that you dropped them. If you drop it from training you must drop it from test as well, using the training file to decide.

5Numbers on wildly different scales

Analysis

Src_Bytes has median 44, 99th percentile 54,540, and maximum 1,379,963,888. The largest value is about 31 million times the median.

Issue detected

Any method that measures distance, and any model that sums weighted inputs, is dominated by whichever column happens to be biggest. Half the rows sit near zero while a few sit near a billion.

Tools available

Five-number summary and percentiles. Boxplots. The IQR rule for flagging outliers. A histogram before and after a transform.

Solution

Apply a log transform such as log(1 + x) to the byte and duration columns, which compresses the tail without discarding rows, then standardize. Fit the transform on training data only and apply the same fitted transform to test, otherwise information from the test set leaks into training.

6A column that is not a feature at all

Analysis

Severity_Score ranges 0 to 21 and averages 20.32 for normal rows versus 18.57 for attack rows. It is the NSL-KDD difficulty score: how many of 21 reference learners classified that row correctly.

Issue detected

It is metadata about the row's difficulty, produced after the fact by other models. It was never observed on the network. Leaving it in the feature matrix is target leakage: the score correlates with the label, so accuracy rises for a reason that will not exist on live traffic.

Tools available

Ask of every column: could a sensor have measured this at the moment the connection happened? Correlation with the label is a hint, but the decisive test is where the value came from.

Solution

Drop Severity_Score from the features. Keep it aside as a way to report which rows are hard. If a result looks too good, look for a leaked column before celebrating.

7Categories that expand into many columns

Analysis

Service takes 70 distinct values in training and 64 in test; Flag takes 11; Protocol_Type takes 3. No category appears in test that is missing from training.

Issue detected

One-hot encoding Service alone turns one column into about 70, most of them almost always zero. Encoders fitted separately on train and test produce different column sets, which is a common and silent bug.

Tools available

Frequency table per category. A chi-square test of independence answers whether a category and the label are related; its p-value says how surprising the association would be if they were unrelated.

Solution

Fit the encoder on training data only, then apply it to test so both end up with identical columns. Group rare services into an other bucket. Keep categories that a chi-square test and your own judgement both say carry signal.

What to do first

Order matters, because some steps change what later steps measure.

  1. Split first. Decide what is training and what is test before looking at anything else.
  2. Drop the columns that are not features: Severity_Score, and any zero-variance column.
  3. Fit encoders and scalers on training only, then apply them to test.
  4. Transform the long-tailed numeric columns, then standardize.
  5. Establish the majority-class baseline. Write it down. It is the number to beat.
  6. Train, then report per-class recall and a confusion matrix, separating attacks seen in training from attacks that were not.

A word on p-values, since we will use them today. A p-value does not tell you whether a result is important, or how large a difference is. It answers one narrow question: if there were really no difference, how often would data look at least this extreme by chance alone? Small p-value, unlikely to be chance. That is all it claims.
