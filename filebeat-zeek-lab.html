Ship logs with Filebeat: a file, a module, and Zeek

Elasticsearch only knows what something sends it. In this lab you install the sender, Filebeat, on two lab machines and point it at three kinds of evidence: a plain file, the system logs of a Linux machine, and the connection records Zeek writes about a network. Each one goes in twice, once as raw lines and once through a module, so you can see exactly what a module adds. Filebeat logs in as a user that can write and do nothing else. Every number on this page was produced by running these steps on the class stack.

1. Look at the cluster2. Install Filebeat3. A user that can only write4. A file as a stream5. The system module6. Zeek, stream and module7. Zeek, live

0Before you start

You need the class docker-elk stack running, with its five services: elasticsearch, logstash, kibana, client-01 and zeek-lab. The compose file is in Appendix A. If docker compose ps in your docker-elk folder does not list all five as running, build the stack first.

You also need cis3370-generate-bundle.zip from Canvas. It holds the capture and the baselines from Lecture 6, made on our own lab machine. Put a copy in each lab machine's data folder. On a Mac or Linux:

cp ~/Downloads/cis3370-generate-bundle.zip ~/docker-elk/client-01/data/

Copy-Item $zip $HOME\docker-elk\zeek-lab\data\

2Install Filebeat on client-01

This follows Elastic's page Filebeat quick start: installation and configuration, step 1, the DEB tab. Two things are different here. First, the version is pinned to 9.5.3, the version the cluster runs, because Filebeat should never be newer than Elasticsearch. Second, the download picks your processor type for you. That is arm64 on an Apple silicon Mac and amd64 on most Windows and Intel machines.

docker compose exec client-01 bash

Then, inside client-01:

apt-get update
apt-get install -y curl unzip nano
cd /tmp
ARCH=$(dpkg --print-architecture)
URL=https://artifacts.elastic.co/downloads/beats/filebeat
curl -L -O $URL/filebeat-9.5.3-${ARCH}.deb
dpkg -i filebeat-9.5.3-${ARCH}.deb
filebeat version

Expected output, with your own processor type in the brackets:

filebeat version 9.5.3 (arm64), libbeat 9.5.3 [...]

The package puts its files in four places, and you will use all of them:

PathWhat is there
/etc/filebeat/filebeat.ymlThe main configuration: what to read and where to send it
/etc/filebeat/modules.d/One file per module. A file ending in .disabled is switched off.
/var/lib/filebeat/registryThe registry: how far into each file Filebeat has already read
/var/log/filebeat/Filebeat's own logs, including the record of any event it could not deliver

The Elastic page says systemctl start filebeat. That does not work here. A container runs one program, not a full operating system, so it has no systemd to start services for you. In this lab you start Filebeat yourself with nohup filebeat -e and stop it with pkill filebeat.

3A user that can only write

Filebeat has two jobs, and they need very different rights.

  • Setup happens once. It creates the index template that says what type each field is, the lifecycle policy that says when old data rolls over, and the ingest pipelines that parse each module's lines. Setup needs administrator rights.
  • Publishing happens all day, on every machine that ships logs. It only adds documents.

A shipper runs on the machine you are watching. If that machine is broken into, the attacker gets the shipper's password from its configuration file. So the publishing account should be able to add documents to its own data and do nothing else: not read, not delete, not create users. Setup is done once by the elastic superuser, and the password Filebeat keeps belongs to a user that cannot undo anything.

PrivilegeWhereWhy Filebeat needs it
monitorclusterCheck the Elasticsearch version and license when it connects
read_ilmclusterCheck that the lifecycle policy exists
read_pipelineclusterCheck that a module's ingest pipeline exists before sending data through it
create_docfilebeat-*Add new documents. It cannot change or delete existing ones.
auto_configurefilebeat-*Create the data stream on first write, and add a field it has never seen to the mapping

Create the role and the user from client-01. The name elasticsearch resolves on the Docker network, so client-01 talks to the cluster directly:

ES=http://elasticsearch:9200

curl -u elastic:changeme -X PUT "$ES/_security/role/filebeat_publisher" \
  -H 'Content-Type: application/json' -d '{
  "cluster": ["monitor", "read_ilm", "read_pipeline"],
  "indices": [
    {
      "names": ["filebeat-*"],
      "privileges": ["create_doc", "auto_configure"]
    }
  ]
}'

curl -u elastic:changeme -X PUT "$ES/_security/user/beats" \
  -H 'Content-Type: application/json' -d '{
  "password": "cis3370-beats",
  "roles": ["filebeat_publisher"],
  "full_name": "Filebeat publisher"
}'

Expected: {"role":{"created":true}}, then {"created":true}. Now prove the restriction holds before you rely on it. Each command prints only the HTTP status code:

curl -u beats:cis3370-beats "$ES/_security/_authenticate?pretty"
curl -s -o /dev/null -w "%{http_code}\n" -u beats:cis3370-beats \
  "$ES/_cluster/health"
curl -s -o /dev/null -w "%{http_code}\n" -u beats:cis3370-beats \
  "$ES/nsl-kdd-train/_search"
curl -s -o /dev/null -w "%{http_code}\n" -u beats:cis3370-beats \
  "$ES/_security/user"
curl -s -o /dev/null -w "%{http_code}\n" -u beats:cis3370-beats \
  -X POST "$ES/lab-probe/_doc" \
  -H 'Content-Type: application/json' -d '{"x":1}'

4A simple file, read as a stream

Start with the simplest thing Filebeat can do: read a file line by line, send every line, then keep watching the file and send each new line as it is written. The input that does this is called filestream. The file is host-baseline.tsv from Lecture 6: a header and 60 rows, one per second of a quiet minute on our lab machine.

cd /home/ubuntu/data
unzip -o cis3370-generate-bundle.zip
mkdir -p lab
cp cis3370-generate-bundle/host-baseline.tsv lab/
wc -l lab/host-baseline.tsv

Expected: 61 lab/host-baseline.tsv. Keep that number: 61 lines should become 61 documents.

Write the configuration

Keep the original file as a reference, then replace it with one that holds only what this lab uses:

cp /etc/filebeat/filebeat.yml /etc/filebeat/filebeat.yml.original

cat > /etc/filebeat/filebeat.yml <<'EOF'
filebeat.inputs:
  - type: filestream
    id: host-baseline
    paths:
      - /home/ubuntu/data/lab/host-baseline.tsv
    fields:
      lab: simple-file

filebeat.config.modules:
  path: ${path.config}/modules.d/*.yml
  reload.enabled: false

setup.kibana:
  host: "http://kibana:5601"

output.elasticsearch:
  hosts: ["http://elasticsearch:9200"]
  username: "beats"
  password: "cis3370-beats"
EOF
SettingWhat it does
type: filestreamRead files line by line and keep following them
id: host-baselineA name for this input. Every filestream input needs its own, because the registry tracks progress by it.
fields.labA label stamped on every document from this input, so you can find them later
filebeat.config.modulesLoad any module that is switched on in modules.d/. None is yet.
output.elasticsearchWhere to send the data, and as which user

Test it before you run it

filebeat test config
filebeat test output

Expected: Config OK, then a connection check that ends:

  talk to server... OK
  version: 9.5.3

A WARN secure connection disabled line in between is correct. This stack speaks plain HTTP, which is fine while nothing leaves your laptop.

Run setup, first as the wrong user

Run setup as beats, the user in the file, and watch it fail:

filebeat setup --index-management
Exiting: ... got 403 from elasticsearch: ... action [cluster:admin/ilm/put] is unauthorized
for user [beats] with effective roles [filebeat_publisher], this action is granted by the
cluster privileges [manage_ilm,manage,all]

That refusal is the role working. Now run the same command as elastic. The -E flags replace the username and password for this one command only, and leave the file alone:

filebeat setup --index-management \
  -E output.elasticsearch.username=elastic \
  -E output.elasticsearch.password=changeme

Expected: Index setup finished.

Start Filebeat and count

nohup filebeat -e > /var/log/filebeat-run.log 2>&1 &

Filebeat now runs in the background and writes its own log to /var/log/filebeat-run.log. nohup keeps it running after you close the terminal. Wait about 20 seconds, then count. Use elastic for this, because beats cannot read:

curl -s -u elastic:changeme "$ES/filebeat-*/_count?q=fields.lab:simple-file"
{"count":61,"_shards":{"total":1,"successful":1,"skipped":0,"failed":0}}

61 lines in the file, 61 documents in Elasticsearch. Now the streaming part. Add one line to the file while Filebeat watches it:

echo "client-01 appended this line" >> lab/host-baseline.tsv

Filebeat looks for changes every 10 seconds. Count again after about 20 seconds and you get "count":62. Nobody restarted anything; the new line was picked up because Filebeat remembers where it stopped reading. That memory is the registry.

If the count stays at 0. When this lab was first written, the role had create_doc and not auto_configure. Filebeat connected, read all 61 lines, and dropped every one. Its log said only this:

Failed to index 61 events in last 10s: events were dropped! Check the event_data log ...

The reason was in /var/log/filebeat/filebeat-events-data-*.ndjson, the file Filebeat keeps for events it could not deliver:

(status=403): action [indices:admin/mapping/auto_put] is unauthorized for user [beats]

The field fields.lab was new to Elasticsearch, and adding a new field to the mapping needs auto_configure. If this happens to you, fix the role, then make Filebeat forget it already read the file, or it will never send those lines again:

pkill filebeat
rm -rf /var/lib/filebeat/registry
nohup filebeat -e > /var/log/filebeat-run.log 2>&1 &

See it in Kibana

  1. Open http://localhost:5601 and log in as elastic.
  2. Stack Management → Data Views → Create data view. Name it filebeat, set the index pattern to filebeat-* and the timestamp field to @timestamp, then save.
  3. Open Discover, pick filebeat, set the time to Last 1 hour, and search fields.lab : "simple-file".

Each document's message is one whole line of the file, tabs and all. Filebeat did not split it into columns, and its @timestamp is the moment Filebeat read the line, not the time written in the line. Remember both facts for section 6.

5The system module

A module is a packaged answer to the question "how do I read this kind of log?" It knows where the files usually live, and it ships an ingest pipeline that splits each line into named fields: user.name, source.ip, event.outcome. The system module reads the two logs every Linux machine keeps: syslog, for general messages, and auth.log, for logins.

Give client-01 something to log

A container has no logging service and no SSH server, so the two files do not exist yet. Install both, and start them by hand. On client-01:

apt-get install -y rsyslog openssh-server
sed -i 's/^module(load="imklog"/#&/' /etc/rsyslog.conf
rsyslogd
mkdir -p /run/sshd && /usr/sbin/sshd
ls -l /var/log/syslog /var/log/auth.log

The sed line switches off the part of rsyslog that reads kernel messages, because a container is not allowed to read the kernel's log. Both files should now exist. If ls says No such file or directory, rsyslog has not finished starting: wait a second and run the ls line again.

Enable the module, then configure it

filebeat modules enable system

Expected: Enabled system. That renamed modules.d/system.yml.disabled to system.yml. Inside it, both parts of the module, called filesets, are still switched off. Switch them on and say where the files are:

cat > /etc/filebeat/modules.d/system.yml <<'EOF'
- module: system
  syslog:
    enabled: true
    var.paths: ["/var/log/syslog"]
  auth:
    enabled: true
    var.paths: ["/var/log/auth.log"]
EOF

Test the module configuration

filebeat test config
filebeat modules list | head -4
Config OK
Enabled:
system

Disabled:

Load the module's pipelines, as elastic

The pipelines are part of setup, so beats cannot load them. Load them as elastic:

filebeat setup --pipelines --modules system --force-enable-module-filesets \
  -E output.elasticsearch.username=elastic \
  -E output.elasticsearch.password=changeme

Expected: Loaded Ingest pipelines. Without --force-enable-module-filesets you get Exiting: module system is configured but has no enabled filesets. That is because with --modules, setup ignores the file you just wrote and looks only at the command line.

Restart Filebeat so it loads the module:

pkill filebeat
nohup filebeat -e > /var/log/filebeat-run.log 2>&1 &

If you started Filebeat before loading the pipelines, its log repeats Failed to connect to backoff(...) together with cluster:admin/ingest/pipeline/put is unauthorized for user [beats]. Filebeat tried to install a missing pipeline itself and was refused. Load the pipelines as above. Filebeat keeps retrying and connects on its own once they exist.

Make some evidence

Write one line to syslog on client-01:

logger -t cis3370 "hello from client-01 through syslog"

Then try to log in to client-01 from the other machine, three times, as three different users. In your second terminal:

docker compose exec zeek-lab bash
apt-get update
apt-get install -y openssh-client
for u in admin root test; do
  ssh -o BatchMode=yes -o StrictHostKeyChecking=no -o ConnectTimeout=5 \
    $u@client-01 true
done

Each attempt prints Permission denied (publickey,password). Back on client-01, tail -5 /var/log/auth.log shows what the server wrote about it:

... sshd-session[3438]: Invalid user admin from 172.21.0.8 port 40830
... sshd-session[3438]: Connection closed by invalid user admin 172.21.0.8 port 40830 [preauth]
... sshd-session[3440]: Connection closed by authenticating user root 172.21.0.8 port 40844 [preauth]
... sshd-session[3442]: Invalid user test from 172.21.0.8 port 40860
... sshd-session[3442]: Connection closed by invalid user test 172.21.0.8 port 40860 [preauth]

The address is zeek-lab's on the class stack. Yours will differ.

Validate that the data is in Elasticsearch

Count documents by where they came from. The field event.dataset names the module and fileset:

curl -s -u elastic:changeme "$ES/filebeat-*/_search?size=0&pretty" \
  -H 'Content-Type: application/json' \
  -d '{"aggs":{"datasets":{"terms":{"field":"event.dataset"}}}}'

You should see buckets for system.auth and system.syslog. The 62 documents from section 4 have no dataset, so they are not in the list. In system.auth, starting sshd adds 2 documents, and each round of three login attempts adds 5. Then ask for the failed logins only:

curl -s -u elastic:changeme -G "$ES/filebeat-*/_search" -d pretty \
  -d q=system.auth.ssh.event:Invalid \
  -d _source=user.name,source.ip,event.outcome

Each hit now has fields the raw line did not: user.name is admin or test, source.ip is zeek-lab's address, and event.outcome is failure. The pipeline handled the newer OpenSSH name for the login process, sshd-session, without any change. In Discover the same search is event.dataset : "system.auth" and event.outcome : "failure".

6Zeek on zeek-lab: a stream, then a module

Now the same exercise on the network side. Zeek reads packets and writes one log line per connection, DNS query and TLS handshake. You will run Zeek on the Lecture 6 capture, ship its conn.log as raw lines, ship the same logs through Filebeat's Zeek module, and compare the two.

Install Zeek

Ubuntu has no Zeek package of its own. The Zeek project publishes one for Ubuntu 26.04, for both processor types. In your zeek-lab terminal:

apt-get install -y curl gnupg ca-certificates unzip nano
REPO=download.opensuse.org/repositories/security:/zeek/xUbuntu_26.04
echo "deb http://$REPO/ /" > /etc/apt/sources.list.d/zeek.list
curl -fsSL https://$REPO/Release.key \
  | gpg --dearmor > /etc/apt/trusted.gpg.d/zeek.gpg
apt-get update
apt-get install -y zeek-core
/opt/zeek/bin/zeek --version

Expected: /opt/zeek/bin/zeek version 9.0.1, or a later 9.0 release. zeek-core is the analysis engine alone, which is all this lab needs.

Install Filebeat on zeek-lab

Run the same seven commands as in section 2, starting at apt-get update. The user and the role already exist, because they live in Elasticsearch and not on a machine.

Turn the capture into Zeek logs

cd /home/ubuntu/data
unzip -o cis3370-generate-bundle.zip
mkdir -p zeek-logs && cd zeek-logs
/opt/zeek/bin/zeek -C -r ../cis3370-generate-bundle/capture.pcap \
  LogAscii::use_json=T
wc -l *.log

PartMeaning
-r capture.pcapRead packets from a file instead of a network interface

Look at one record, and note its uid. You will look this connection up twice:

head -1 conn.log

Ship conn.log as a stream

This is section 4 again, with one addition. Each line is JSON, so a parser called ndjson turns the line into fields, and target puts them under one name so they cannot collide with anything else:

cp /etc/filebeat/filebeat.yml /etc/filebeat/filebeat.yml.original

cat > /etc/filebeat/filebeat.yml <<'EOF'
filebeat.inputs:
  - type: filestream
    id: zeek-conn-raw
    paths:
      - /home/ubuntu/data/zeek-logs/conn.log
    parsers:
      - ndjson:
          target: "zeek_raw"
    fields:
      lab: zeek-stream

filebeat.config.modules:
  path: ${path.config}/modules.d/*.yml
  reload.enabled: false

setup.kibana:
  host: "http://kibana:5601"

output.elasticsearch:
  hosts: ["http://elasticsearch:9200"]
  username: "beats"
  password: "cis3370-beats"
EOF

filebeat modules enable zeek

7Zeek, live

So far Zeek read a recording. Now it watches zeek-lab's own network card while client-01 scans it, and Filebeat ships each record as Zeek writes it. The module already lists the zeek-live folder, so nothing in Filebeat changes. When the file appears, Filebeat finds it within about 10 seconds. On zeek-lab:

mkdir -p /home/ubuntu/data/zeek-live && cd /home/ubuntu/data/zeek-live
/opt/zeek/bin/zeek -C -i eth0 LogAscii::use_json=T > zeek.out 2>&1 &
hostname -i

-i eth0 means listen on the network card. Note the address hostname -i prints. On client-01:

apt-get install -y nmap
nmap -sT -p 1-1000 zeek-lab
hostname -i
Not shown: 1000 closed tcp ports (conn-refused)
...
Nmap done: 1 IP address (1 host up) scanned in 0.60 seconds

Back on zeek-lab, stop Zeek politely so it writes out everything it is holding, then count:

pkill -INT zeek
wc -l conn.log
cat reporter.log

On the class stack: 1001 conn.log, and the reporter log said 2006 packets received on interface eth0, 0 (0.00%) dropped. A capture that drops packets misses connections, so check that number every time you capture. Now ask Elasticsearch about the live file only:

curl -s -u elastic:changeme "$ES/filebeat-*/_search?size=0&pretty" \
  -H 'Content-Type: application/json' -d '{
  "query": {"bool": {"filter": [
    {"term": {"event.dataset": "zeek.connection"}},
    {"term": {"log.file.path": "/home/ubuntu/data/zeek-live/conn.log"}}
  ]}},
  "aggs": {
    "from":  {"terms": {"field": "source.ip"}},
    "state": {"terms": {"field": "zeek.connection.state"}},
    "ports": {"cardinality": {"field": "destination.port"}}
  }
}'

On the class stack: 1,001 documents. 1,000 came from client-01's address, all REJ, and one record was zeek-lab's own traffic. That is the scan, seen from the target, a few seconds after it happened. The bundle counts do not change: Filebeat's registry remembers it already sent those files, so restarting it never sends them twice.

8Take the password out of the file

filebeat.yml still holds the beats password in plain text. Filebeat has a keystore for exactly this. Do it on both machines:

filebeat keystore create
echo -n "cis3370-beats" | filebeat keystore add BEATS_PWD --stdin
filebeat keystore list
sed -i 's|password: "cis3370-beats"|password: "${BEATS_PWD}"|' \
  /etc/filebeat/filebeat.yml
grep password /etc/filebeat/filebeat.yml
filebeat test output
pkill filebeat
nohup filebeat -e > /var/log/filebeat-run.log 2>&1 &

Expected: the list prints BEATS_PWD, the file now says password: "${BEATS_PWD}", and the output test still ends with talk to server... OK. A line sent after the restart arrived as normal. The password is still on the machine, because Filebeat has to send it. The keystore keeps it out of a file people read, copy and paste into tickets.

  # Elasticsearch, such as 'logstash_internal' and 'kibana_system', with the

  # roles required by some of these users.
